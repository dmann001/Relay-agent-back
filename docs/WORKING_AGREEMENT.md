# Working Agreement

This document outlines how the team will collaborate, communicate, and manage responsibilities throughout the duration of the project. The goal of this agreement is to ensure transparency, accountability, and a respectful working environment for all team members.

---

## 1. Meeting Information

- **Weekly Meeting Day and Time:**  
  Once per week, time agreed upon by the team at the start of each sprint.

- **Meeting Platform / Location:**  
  - Primary: WhatsApp  
  - Backup: Microsoft Teams  
  - In-person meetings may be scheduled if all members agree.

Attendance is expected for all scheduled meetings unless prior notice is given.

---

## 2. Communication Expectations

- **Preferred Communication Channels:**  
  - WhatsApp (primary, for daily communication)  
  - GitHub Issues and Pull Requests (for task-related discussion)

- **Expected Response Time:**  
  - Within **24 hours** on weekdays  
  - Within **48 hours** on weekends unless marked as urgent

Team members should clearly communicate availability changes or delays as early as possible.

---

## 3. Accountability Rules

To ensure fair contribution and accountability, the team agrees to the following consequences:

### Missing Meetings
- First occurrence: Verbal reminder
- Repeated occurrences: Reassignment of responsibilities and reporting concerns to the professor if unresolved

### Repeated Lateness
- Reduced participation in decision-making for the affected sprint

### Lack of Participation
- Assignment of extra documentation or support tasks
- Possible reporting to the professor if behavior continues

### Failure to Respond to Teammates
- Loss of task ownership
- Responsibilities may be reassigned to ensure project progress

All accountability measures aim to resolve issues constructively and fairly.

---

## 4. GitHub Workflow Agreement

- **Main Branch Protection:**  
  - Direct pushes to the `main` branch are **not allowed**.

- **Code Merging Process:**  
  - All changes must be made in a separate branch.
  - Changes are merged into `main` via Pull Requests only.

- **Pull Request Review Expectations:**  
  - A Pull Request requires at least one approving review from a team member other than the author before it can be merged.
  - Pull Requests should include a clear description of changes.

- **Branch Naming Conventions:**  
  - `feature/short-description`
  - `docs/short-description`
  - `fix/short-description`

---

## 5. Testing Requirements

- **Minimum Testing Expectations:**  
  - Code must be manually tested to confirm it does not break existing functionality.
  - Documentation changes must be reviewed for clarity and accuracy.

- **Automated Testing:**  
  - Automated tests will be added where applicable as the project evolves.

- **Verification Responsibilities:**  
  - The Pull Request author is responsible for initial testing.
  - Reviewers must verify that changes meet requirements before approving the Pull Request.

No code may be merged unless testing and verification requirements are met.

---

By contributing to this project, all team members agree to follow this working agreement to support effective collaboration and project success.
